# 工作项目 · Zenflux AI Agent 平台前端

> 我在 Zenflux 担任全栈开发工程师，负责 AI Agent 平台（ZenfluxAIOS）的前端架构。本页只在概念层面介绍我负责的方向，不涉及内部代码、接口和客户数据。

## 一、A2UI：Agent 驱动的生成式 UI

A2UI（Agent-to-UI）是一套让 Agent 直接“说出界面”的协议：Agent 不再只返回文字，而是输出一段**声明式的界面描述**，前端运行时负责校验、映射成真实组件并渲染成可交互界面。

我主导了 A2UI 的协议与前端架构设计，并实现了它的一组前端包：

- **运行时内核**：显式的渲染状态（加载中 / 就绪 / 降级 / 错误），对重复和乱序消息做幂等处理
- **组件目录（Catalog）**：基于 Manifest 的组件协议和注册，决定 Agent 能用哪些组件、每个组件接受哪些属性
- **Widget SDK**：组件作者唯一的导入入口，隔离平台内部实现
- **设计器外壳**：字段编辑器注册表，让同一份协议既能被 Agent 生成，也能被人在设计器里配置
- **多端适配**：图表、地图运行时和小程序桥接，同一份描述可以在 Web 和小程序上渲染

## 二、Agent 对话：流式卡片协议与嵌入桥

Agent 的回复是**边生成边展示**的。我设计了基于 WebSocket 的流式卡片协议：消息以 `start` 开始，用一连串 `delta` 增量补全，前端把增量**归一化**成稳定的展示结构，于是“生成中的卡片”和“完成的卡片”使用同一套渲染逻辑。

围绕对话体验，我还负责：

- 流式渲染体验：逐行渐显、长消息滚动性能、生成中的输入状态控制
- **智能体意图契约**：Agent 向宿主页面声明“想做什么”（跳转、打开面板、提交表单），由宿主按策略决定是否执行
- **嵌入桥协议**：业务 H5 / 第三方页面嵌入工作台时的双向通信与能力协商
- MCP 服务目录与管理界面

## 三、Widget 开放生态

为了让第三方开发者也能给平台写组件，我负责了 Widget 从开发到上线的完整生命周期：

- **Manifest 唯一声明来源**：组件的名字、属性、配置项都写在 Manifest 里；配置面板根据 `settings_schema` 自动生成
- **Studio 源码模板**：开发者下载模板在本地开发，本地离线构建的形状与平台正式构建一致
- **宿主桥 SDK**：组件只通过 SDK 和宿主通信，平台升级不破坏组件
- **发布生命周期**（后端用 Go 实现）：沙盒构建 → 审批与快照 → 说明书冻结生效 → 页面钉版本引用 → 可回退

## 四、设计系统与 Design Token

- 定义了一份 **34 项的工作台主题 Token 合同**：每套主题都必须把 34 项的亮色和暗色取值写满，不依赖层叠回落
- 用 **JSON Schema + 校验器 + 跨语言夹具 + 契约测试** 保证不同语言、不同端读到的是同一份主题
- 修复焦点环、危险色的对比度，使其满足可访问性要求；支持多套主题预设一键切换
- 令牌包按语义化版本发布，CI 会检查主题改动是否同步升级了版本

## 五、多端 Monorepo、CI 与 AI 编码治理

- 从零搭建并维护前端 Monorepo（pnpm + Turbo）：C 端工作台、机构 / 平台后台、H5、小程序、桌面端、文档站，加上一组共享包（UI、图标、多语言、表单 Schema、认证等）
- 主栈统一到 React 19 + TypeScript + Vite + Zustand + React Query + Tailwind CSS 4
- 多应用 CI 流水线：按应用和环境拆分构建与部署
- **AI 编码治理**：为仓库编写 AGENTS.md、Rules、Skills，配合 commit hook、commitlint、样式类名门禁，让 AI 编码工具在规范内稳定交付
- 维护跨团队的接口文档中心（Markdown + llms.txt），让人和 AI 都能读懂接口
