# 为 Agent 对话设计流式卡片协议

<Draft />

大模型的回复是一个字一个字生成的，用户也早就习惯了“打字机”式的输出。可一旦回复里不只有文字，还有**可点击的卡片**（订单、表单、图表、确认按钮），事情就复杂了：卡片的字段同样是逐步生成的，前端既要尽早把它显示出来，又不能让用户点到一张“半成品”。这篇文章总结我在设计流式卡片协议时的几条经验。

## 1. 先把消息生命周期定死：start / delta / done

最容易出问题的，是“消息什么时候开始、什么时候结束”没有明确的信号。我的建议是用三类事件把生命周期固定下来：

```json
{ "type": "message.assistant.start", "messageId": "m1", "seq": 0 }
{ "type": "message.assistant.delta", "messageId": "m1", "seq": 1, "path": "text", "append": "正在为你" }
{ "type": "message.assistant.delta", "messageId": "m1", "seq": 2, "path": "cards[0].title", "set": "订单确认" }
{ "type": "message.assistant.done",  "messageId": "m1", "seq": 9 }
```

- `start` 只负责创建占位消息，让界面立刻出现一个“正在生成”的气泡
- `delta` 只描述**增量**，并且带上 `seq`。前端可以凭它丢弃重复帧、发现丢帧
- `done` 是唯一的“完成”信号。只有收到它之后，卡片上的动作按钮才可以点

不要用“一段时间没收到新数据”来推断结束，网络抖一下就会误判。

## 2. 增量要“可合并”，而不是“可拼接”

文字增量可以直接拼接，卡片不行。如果后端每次都推一整张卡片的 JSON 片段，前端就只能做字符串拼接，再尝试 `JSON.parse`，中途解析失败是常态。

更稳妥的做法，是让每个 delta 都带上**路径和操作**（`set` / `append` / `remove`）。前端维护一棵消息状态树，按路径把增量合并进去。这样每一帧之后，状态都是合法的结构，渲染层永远不用面对半截 JSON。

## 3. 归一化层：生成中和完成态共用一套组件

协议层合并好的状态，往往还不适合直接渲染：字段可能缺失，类型也可能还没确定。我会在中间加一层**归一化**：

- 把缺失字段补成明确的“占位”状态，而不是 `undefined`
- 把不同来源的卡片（历史消息、实时流、刷新后的重放）统一成同一个前端模型
- 给每张卡片算出一个 `ready` 状态，交给渲染层决定是显示骨架屏，还是允许交互

这样，“正在生成的卡片”和“历史里的完整卡片”走的是**同一个组件**，不会出现两套样式、两套 bug。页面刷新后重放历史消息，也只是把增量重新喂一遍。

## 4. 渲染性能：逐行渐显与滚动

流式输出很容易拖垮渲染：每秒几十帧 delta，如果每帧都触发整棵消息列表重渲染，长对话就会卡。几个实用的做法：

- 用 `requestAnimationFrame` 把同一帧内到达的多个 delta 合并成一次提交
- 只让“正在生成的那条消息”订阅流，历史消息保持稳定引用
- 只有用户本来就在底部时才自动滚动；用户往上翻看时，不要把他拽回底部
- 生成过程中，输入框的回车行为要明确：是排队、打断，还是禁止发送，要提前定好，不要留给偶然

## 5. WebSocket 的坑：帧大小与重连

用 WebSocket 推送时，有一个容易被忽略的坑：**单帧大小限制**。不少服务端和网关对单条消息的大小有限制，超过就直接以 1009（Message Too Big）关闭连接。常见的触发场景是：用户发送了一大段文本，或者一次 delta 里塞进了整张大表格。

应对办法：

- 协议层规定单个 delta 的大小上限，大内容**分片**发送，或者改成“先上传、再引用”
- 客户端发送前先检查体积，超限时给出友好提示，而不是让连接断掉
- 重连之后，用 `messageId + seq` 请求补发，并配合幂等合并，保证不重复、不丢失

## 6. 动作交给宿主：意图而不是命令

卡片上的按钮，最终要触发真实操作，比如跳转页面、打开面板、提交表单。我的建议是让 Agent 输出**意图**（“想打开订单详情”），由宿主页面按策略决定是否执行、是否需要用户二次确认。这样既能防止模型越权，也让同一张卡片可以在不同宿主（Web、桌面、H5 嵌入）里各自适配。

## 小结

流式卡片协议的核心是三件事：**生命周期明确、增量可合并、渲染只认归一化后的模型**。做到这三点，再加上帧大小和重连的兜底，“边生成边交互”的体验才能既流畅又可靠。
