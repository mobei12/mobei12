# Design Token 合同：用 JSON Schema 和契约测试守住多端主题

<Draft />

很多团队都有 Design Token，但 Token 往往只是“一堆 CSS 变量”：谁都能加，谁都能改，缺了某个值就靠层叠回落。一旦平台需要支持多套主题、暗色模式，还要让 Web 以外的端（小程序、桌面、服务端渲染、其他语言）读到同一份主题，这种松散的方式很快就会失控。我的经验是：**把 Token 当成合同来管理**。

## 1. 什么是“Token 合同”

合同的意思是：**明确列出哪些 Token 属于主题，每套主题都必须为每一项给出完整取值**。

在我们的实践里，工作台主题合同一共收敛到 34 项，例如背景、前景、主色、边框、焦点环、危险色等。合同有几条规则：

- 每套主题预设都必须**写满** 34 项的亮色和暗色两套取值，不允许靠层叠回落来补缺项
- 合同之外的 Token（品牌色、字号、圆角等）**不随主题变化**，只定义一次
- 可以被外部覆写的 Token 清单也属于合同的一部分，而且越窄越好

把范围收窄是有意为之：可覆写的项越少，主题之间越不容易出现“某个组件在某套主题下看不清”的问题。

## 2. 用 JSON Schema 描述合同

合同不能只写在文档里，必须是**机器可校验的**。我们用 JSON Schema 来描述一份主题：

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["light", "dark"],
  "properties": {
    "light": { "$ref": "#/$defs/palette" },
    "dark":  { "$ref": "#/$defs/palette" }
  },
  "$defs": {
    "palette": {
      "type": "object",
      "required": ["background", "foreground", "primary", "ring", "destructive"],
      "additionalProperties": false
    }
  }
}
```

`required` 保证没有缺项，`additionalProperties: false` 保证没人偷偷加私有 Token。配合一个小的校验器，再把颜色格式、取值范围检查一起做掉。

## 3. 可访问性也写进合同

颜色合不合格，不应该靠肉眼判断。我们把**对比度检查**也放进了校验流程：前景与背景、焦点环与背景、危险色在浅色主题下的对比度，都必须达到 WCAG 的门槛。很多“浅色主题下红色按钮看不清”“键盘焦点环看不见”的问题，都是这样被提前拦住的。

## 4. 跨语言夹具：让每个端读到同一份主题

难点在于：Token 不只给 CSS 用。服务端可能需要生成主题资产，其他语言的服务可能需要校验租户上传的主题。如果每种语言各写一份解析逻辑，迟早会不一致。

我们的做法是准备一组**夹具（fixtures）**：

- 一批“合法主题”和“非法主题”样例 JSON，非法样例覆盖缺项、多项、格式错误、对比度不足等情况
- 每个样例都附带期望的校验结果
- JSON 在比较前做**规范化序列化**（键排序、数字格式统一），避免不同语言序列化结果不同导致误报

每种语言的实现都必须跑通同一组夹具，这就是**契约测试**：不关心你内部怎么实现，只关心对同一个输入是否给出同一个结论。

## 5. 发布：版本号就是合同的版本

令牌包按语义化版本发布：

- 新增可选能力，升 minor
- 收窄或删除合同项，升 major
- 只修复取值，升 patch

CI 里加了两道门：修改主题源文件时必须同时升级包版本；发布用的 tag 必须和包版本一致。这样下游永远知道自己拿到的是哪一版合同。

## 6. 落地到组件：只用语义 Token

合同建好之后，还需要把业务代码里写死的颜色迁移过来。我们的经验是：

- 状态色（成功、警告、错误）统一走共享组件，不让业务模块自己挑颜色
- 用 lint 规则禁止新增硬编码颜色和未知的样式类名
- 主题切换只改一个属性（例如 `data-workspace-theme`），组件对主题无感

## 小结

把 Token 从“变量集合”升级成“合同”，关键在四件事：**明确范围、机器校验、跨语言契约测试、版本化发布**。前期多花一点时间，换来的是多主题、多端、多语言场景下长期稳定的主题体系。
